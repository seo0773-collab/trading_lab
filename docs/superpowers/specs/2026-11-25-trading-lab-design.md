- 작성일: 2026-11-25
- 상태: 최종안 (사용자 승인 대기)
- 참고: 기존 `seo0773-collab/trading_lab` 저장소는 **읽기 전용 참고용**. 코드·스펙을 골라 옮길 수 있으나 기존 저장소는 수정하지 않는다.

표기: **[결정]** = 사용자가 정한 것, **[제안]** = 설계자가 정한 것(사용자가 뒤집을 수 있음), **[미정]** = 아직 답이 필요한 것.

## 1. 의도 (왜 만드는가)

한국·미국 주식 시장을 상시 감시하며 **스펙 문서(spec.md)에 적힌 전략대로 자동 매매**하는 시스템을 만든다.
전략은 고정되어 있지 않고 **수행 → 검토 → 스펙 업데이트 → 수행** 루프로 계속 개선된다.

핵심 문제의식: 운영 기록·메모·계획 문서는 쌓이는 순간부터 낡는다(기존 저장소의 루트 `*_plan.txt` 약 5.7천 줄, `plans/`, 스펙 안의 `[정정]`·취소선 누적이 그 예). 신규 시스템은 **배운 것을 즉시 스펙 본문에 녹여서**, 스펙이 언제나 "지금의 진실" 하나만 담게 한다.

## 2. 목표 / 비목표 / 안티목표

**목표**
- G1. 스펙 = 동작의 근거. 스펙의 모든 규칙이 코드와 테스트로 1:1 추적된다.
- G2. 루프 자동화: 검토 세션이 기록을 읽고 스펙+코드+테스트 수정안을 PR로 올린다. 사람이 머지하면 봇이 반영한다.
- G3. 가치 기반 전략: 밸류에이션 + 이벤트 가치 + 연관 산업군 전파 → 타겟 밸류. EMA/RSI 추세는 보조(타이밍).
- G4. 백테스트와 실거래가 같은 전략 코드 경로를 쓴다.

**비목표 (이번 설계 범위 밖)**
- 공매도, 레버리지, 파생상품. (인버스 ETF는 스펙 확장 시 검토)
- 초단타/틱 단위 매매.
- 증권사 확정 및 실계좌 연동 (인터페이스만 정의, 구현은 계좌 결정 후).
- 웹 대시보드. (알림 + 데이터 파일로 시작)

**안티목표 (기술적으로 돌아가도 실패인 것)**
- A1. 스펙과 실제 동작이 어긋난다.
- A2. 스펙 밖(서술 메모, 계획 문서, 저널)에 판단 근거가 쌓인다.
- A3. 사람 승인 없이 돈을 움직이는 로직이 바뀐다.
- A4. 스펙/모델 오류가 손실 상한 없이 실거래에 전파된다.

## 3. 제약

- 실행 호스트: **[결정]** 집 PC의 VirtualBox Ubuntu VM. 인바운드 접속 없음(공유기 포트 개방 안 함).
- 클라우드 Claude 세션은 휘발성 → 상주 봇 불가. 검토 세션 전용.
- 시장: **[결정]** 한국 + 미국 주식, 롱 기본.
- 증권사: **[결정]** 추후 검토. 그 전까지 페이퍼 체결.
- 유료 데이터는 최소화. [제안] 무료 소스로 시작: 가격(pykrx/FinanceDataReader, yfinance), 공시(DART OpenAPI, SEC EDGAR), 재무(DART 재무제표, EDGAR XBRL companyfacts).

## 4. 접근 (Approaches)

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. 단일 저장소, 백테스트=실거래 코드 경로** | specs/·src/·models/·tests/ 한 저장소. 전략 코드는 하나, 데이터 입력과 체결기만 교체 | 스펙·코드·테스트를 한 PR로 묶어 CI로 어긋남 차단. 백테스트 결과를 신뢰 가능 | 엔진 자체 구현 필요 |
| B. 스펙 저장소 분리 | 스펙만 별도 저장소 | 스펙 이력이 깔끔 | 스펙과 코드가 다른 PR로 바뀌어 A1 방지 불가 |
| C. 기존 프레임워크(backtrader, nautilus 등) | 엔진 재사용 | 엔진 수고 감소 | 한국 주식·공시·가치모델은 어차피 직접 구현, 프레임워크 제약 추가 |

**[결정] A 채택.** 이유: G1/A1(스펙-코드 일치 강제)을 구조적으로 보장할 수 있는 유일한 안.

## 7. 스펙 형식과 스펙-코드 일치

### 7.1 전략 스펙 구조 [제안]

```markdown
# <strategy_id>
상태: paper | live-small | live      ← 단계 (단계 전환 조건은 본문 규칙으로)
모델: value_model@v3                 ← 사용하는 가치판단 모델 버전

## 목적
## 유니버스            UNIV-1, UNIV-2 ...
## 진입                ENTRY-1 ...
## 청산                EXIT-1 ...
## 포지션 사이징        SIZE-1 ...
## 단계 전환 조건       STAGE-1 ...
## 알려진 한계          (현재 유효한 것만. 해소되면 삭제)
```

- 규칙은 `- **ENTRY-1**: <한 문장, 측정 가능한 조건>` 형식.
- **이력 금지**: `[정정]`, 취소선, "변경 이력", 날짜별 메모 섹션을 두지 않는다. 과거는 git 히스토리와 PR이 보관.
- 수치 근거가 필요하면 "현재 유효한 실측치"만 적고, 출처는 해당 PR 링크.

### 7.2 일치 강제 (CI) [제안]

1. 스펙의 모든 규칙 ID → `tests/rules/` 에 `test_<ID>` 가 최소 1개.
2. `src/` 의 `# RULE: <ID>` 주석 → 스펙에 존재하는 ID만 허용.
3. 스펙에서 ID가 삭제되면 대응 코드·테스트도 같은 PR에서 삭제돼야 통과.
4. `config/risk_limits.yaml` 변경 PR은 CODEOWNERS(사용자) 승인 필수. 검토 세션은 이 파일을 수정하지 않는다(CI가 봇 계정 변경을 실패 처리).

## 8. 전략 로직

### 8.1 가치 축 [결정: 재무 논리 + 과거 반응 보정]

1. **밸류에이션 (기준 가치)**: 종목별 적정가치 = f(이익·성장 추정, 섹터 기준 멀티플). [제안] 1차 버전은 상대 멀티플(PER/PBR/EV-EBITDA의 섹터 대비 위치)로 시작, DCF는 이후.
2. **이벤트 가치**: 이벤트 → 이익/성장 추정치 변화량(재무 논리) → 적정가치 변화. 변화량에 곱하는 **반응 계수**는 과거 이벤트의 초과수익률(이벤트 스터디)로 보정.
3. **연관 산업군 전파**: 섹터 간·섹터 내 상관 구조(수익률 상관 + 공급망/동종 분류)로 이벤트 영향을 이웃 종목에 계수만큼 전파. 전파 계수도 과거 반응으로 보정.
4. **타겟 밸류** = 기준 가치 + Σ(이벤트 조정) + Σ(전파 조정). 괴리율 = 타겟 / 현재가 − 1.

이벤트 종류 1차 [제안]: 실적 발표(컨센서스 대비 서프라이즈), 가이던스 변경, 주요 공시(유상증자·자사주·M&A·대규모 수주). 뉴스·정책은 이후 단계.

### 8.2 보조 축 [결정: EMA + RSI]

- 괴리율이 진입 임계를 넘은 종목에 대해, EMA 추세 정렬 + RSI 과열/과매도 조건으로 진입·청산 타이밍 결정.
- 세부 파라미터는 전략 스펙의 규칙으로.

### 8.3 진행 단계 [제안]

| 단계 | 내용 | 완료 조건 |
| --- | --- | --- |
| M1 | 플랫폼 + EMA/RSI 단독 전략, 페이퍼. 루프 1회 이상 완주(검토 PR → 머지 → 봇 반영) | 1주 무중단 페이퍼 + CI 일치 검사 동작 |
| M2 | 밸류에이션 기준 가치 + 괴리율 진입 | 백테스트에서 M1 대비 비교 지표 산출 |
| M3 | 이벤트 가치 (실적·공시), 계수 보정 파이프라인 | 표본 외 검증 기준 충족(모델 스펙에 정의) |
| M4 | 연관 산업군 전파 | 동일 |
| M5 | 증권사 결정 → 실계좌 어댑터 → 소액 실거래 | 단계 전환 규칙(STAGE-*) 충족 |

## 9. 리스크 하드 리밋 [제안]

`config/risk_limits.yaml` — 스펙보다 우선, 사람만 수정.
- 종목당 최대 비중, 동시 보유 종목 수 상한
- 포지션당 최대 손실(손절), 일일 손실 한도 → 도달 시 신규 진입 정지 + 알림
- 계좌 누적 낙폭 한도 → 도달 시 전체 정지(수동 재개)
- 주문 단위 상한(금액), 1일 주문 횟수 상한 (폭주 방지)
- 실계좌 단계에서는 가능하면 증권사 서버 측 손절/조건 주문도 함께 사용

## 10. 운영

- **시간**: 한국장 09:00–15:30 KST, 미국장 23:30–06:00 KST(서머타임 22:30–05:00). 장중 = 가격 감시 + 주문. 장외 = 공시·뉴스·실적 수집, 타겟 밸류 재계산, 다음 장 주문 계획 작성.
- **배포**: updater가 `main`을 주기적으로 fetch → 새 커밋이면 별도 디렉터리에 체크아웃 → 테스트 통과 시에만 전환. 전환은 장 마감 후 또는 무포지션 시점이 아니라도 가능하되, **기존 포지션은 보유한 채 다음 진입부터 새 규칙 적용**. 실패 시 이전 버전 유지 + 알림.
- **상주**: systemd 서비스(자동 재시작), VM 자동 부팅, 호스트 절전 끔. healthcheck가 주기적 하트비트 알림.
- **장애 시**: 데이터 소스 실패 → 해당 단계 건너뛰고 신규 진입 보류. 브로커 실패 → 신규 진입 정지 + 알림.
- **비밀값**: API 키는 VM 로컬 `.env`(저장소 제외). 저장소에 비밀값 금지.

## 11. 검토 루프

1. 봇이 매일 장 마감 후 `ledger/summary/`(체결, 신호, 예측 vs 실제 반응, 리밋 발동)를 별도 브랜치에 push. [제안] 원시 로그는 VM 로컬 보관, 저장소엔 요약 데이터만.
2. 클라우드 검토 세션이 정기 실행(예: 매일 1회, 한국장 시작 전). 요약 + 스펙 + 코드를 읽고:
   - 개선점이 있으면 **스펙 본문 + 코드 + 테스트**를 함께 고친 PR.
   - PR 본문: 근거 데이터, 백테스트 비교, 영향받는 규칙 ID.
   - 개선점이 없으면 PR 없음(빈 보고서·저널 작성 금지).
3. 사람이 리뷰·머지 → updater가 반영.
4. 가치판단 모델 재보정도 같은 경로: `models/<id>/<새 버전>` + 모델 스펙 갱신 + 검증 수치를 한 PR로.

## 13. 범위 결정

- **유니버스 [결정]**: 관심 산업군 몇 개로 좁게, 그 산업군의 한·미 종목. 구체 산업군과 종목 목록은 첫 전략 스펙의 `UNIV-*` 규칙으로 정한다(시스템 고정값 아님). [제안] 시작 규모는 산업군 2~3개, 종목 수십 개.
- **보유 기간 [결정]**: 스윙(며칠~몇 주). [제안] 판단은 일봉 + 1시간봉, 장중에는 손절·리밋 감시와 계획된 주문 집행 위주. 분봉 실시간 데이터는 쓰지 않는다.
- **LLM [결정]**: 사용한다. 단, 14절의 작업 분류 원칙을 따른다.

## 14. 작업 분류 원칙: LLM 추론 vs 스크립트 도구 [결정]

봇 파이프라인과 검토 세션 모두에 적용한다.

| 작업 성격 | 담당 | 예 |
| --- | --- | --- |
| **추론이 필요한 것** (비정형 해석, 판단, 분류) | LLM | 공시 본문·뉴스 → 이벤트 종류·대상 종목·핵심 수치 추출, 기록을 보고 스펙 개선점 도출 |
| **계산이 필요한 것** (수치, 통계, 지표) | 스크립트 | 밸류에이션·괴리율, EMA/RSI, 백테스트, 이벤트 스터디 초과수익률, 계수 보정, 성과 지표 |
| **반복되는 것** (같은 절차를 되풀이) | 스크립트 | 데이터 수집, 요약 생성, 정형 공시 파싱, 리포트 집계 |

규칙:
- LLM은 숫자를 계산하지 않는다. 계산이 필요하면 스크립트를 도구로 호출하고 그 결과를 쓴다.
- LLM 출력은 정해진 스키마(JSON)로 받고, 스키마 검증을 통과한 것만 다음 단계로 넘긴다. 검증 실패 시 해당 이벤트는 반영 보류 + 기록.
- 같은 추론 결과가 반복되면(예: 특정 공시 유형이 늘 같은 방식으로 해석됨) 그 부분은 규칙/스크립트로 내린다.
- **반복 업무 감지 → 스크립트 도입 검토**: 검토 세션은 자신이나 봇이 같은 절차를 반복하고 있음을 발견하면, 이를 스크립트로 만드는 PR을 제안한다. 도입한 스크립트는 `src/tlab/tools/`(또는 해당 모듈)에 두고 테스트를 붙이며, 시스템 스펙(`specs/_system.md`)의 도구 목록에 등록한다.
- [제안] LLM 호출은 결과를 입력 해시 기준으로 캐시해 같은 공시를 두 번 해석하지 않는다. 사용한 모델·프롬프트 버전을 결과와 함께 기록한다(백테스트 재현용).
